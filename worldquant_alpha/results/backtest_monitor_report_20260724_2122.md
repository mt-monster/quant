## ③ 回测效率结论（详细）

### 3.1 实测吞吐 vs 基准
- 基准 `bench_v34_sim_speed`：**multi(8)=86.1 α/hr** vs single 逐条=54.3 α/hr → **speedup 1.59×**。
- **V43 = 71.3 α/hr**：低于 86.1 基准约 17%。缺口源于 `event_relation` 数据集比基准用的 EUR 字段更重（单条回测计算/响应更慢），属**数据集固有成本，非配置错误**（冷却仍是 45s，与基准一致）。
- **tabbit ≈ 100 α/hr**：3 路并行单模拟、批间无冷却，反而略高于 V42 的 multi-sim 批次吞吐——说明其教程账号虽无 multi-sim，但 3 并发持续打满也能逼近多模拟效率。

### 3.2 各任务是否跑在最大并发档
- **V43**：multi-sim `BATCH=8` + 45s 冷却 = 该模式**设计最优**档（基准即此配置）。未达平台理论绝对上限（批大小>8 从未测过）。
- **tabbit**：`CONCURRENCY=3` = 其**教程账号硬上限**（无 multi-sim 权限），已"永远默认打满"。
- 两者均**非 CPU 瓶颈**（CPU≈0.1%），受限于 WQ 平台延迟 + 限流，无法靠本机算力提速。

### 3.3 平台整体并发利用率
- **当前同时跑 2 个独立作业**（V43 + tabbit），且分属**两个不同账号**（126 / gmail）→ 限流/额度互不干扰，叠加约 **8(V43 批) + 3(tabbit) = 最高 11 路并发模拟**。
- 这比单作业（仅 V43 或仅 tabbit）显著提升了平台并发槽位利用率。
- **但仍有闲置空间**：系统可再拉起第 3 个独立数据集/账号的扫描任务进一步压榨总吞吐（前提是另有账号且不触发 429）。

### 3.4 批大小 >8 的信息缺口
- 基准只对比 multi(8) vs single，**未测 multi(16)/multi(24)**。故只能证明"8 条/批显著优于逐条"，**不能断言 8 是平台绝对最优批次**。若要确认拐点，需补一次基准（可选验证，有 429 风险）。

### 3.5 核心论断（固定结论）
- **V31–V43 生产 + tabbit 教程，累计 ~2000+ 条 alpha，仅 V39b 上线 1 条**。
- 当前 3 个方向的信号质量：**V43 最佳 0.35（闸门 1.58）、tabbit 0/272（Fitness 死结）、V42 已完 0/200**。
- **瓶颈是信号发现，不是吞吐/并发**。在出候选之前，提并发、加并行、堆量，都只是加速"挖出 0 候选"。

### 3.6 可行动建议
1. **盯 V43**：它是唯一新方向（事件关系），早期 88/≈150–200、最佳 0.35 偏低但尚在早期，给足跑完的空间；若最终仍 0 候选，与前述家族同判死结。
2. **处置 tabbit**：已确认 0/272 候选（Fitness 结构性失败），持续空转。建议**先停**（省资源），或换 `implied_vol`/`gamma` 类字段 + 行业中性再试，而非同模板堆量。
3. **勿为吞吐调并发**：当前 2 作业并行已较好利用平台；除非新增独立账号任务，否则提并发无收益。
4. **范式转向优先级最高**：围绕 V39b 成功风格（低自相关 + 行业中性 + W189/d3/SECTOR/t1）做扩展，是比继续扫新数据集更可能出候选的路径。
