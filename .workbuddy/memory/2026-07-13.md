### 🔴 重大坑：wd_lib_wrapper.py 缺失 + 孤儿模拟占满并发配额
- **现象**：挖矿脚本 `from wd_lib_wrapper import WqApiSimple` 报 `ModuleNotFoundError: No module named 'wd_lib_wrapper'`。全盘 `find` 确认该文件**根本不存在**（之前会话摘要里"冒烟跑通"是误记）。真正的客户端是 `wd_lib/client.py` 的 `WorldQuantClient`，但历史挖矿脚本依赖的是已消失的薄封装 `WqApiSimple`。
- **修复**：重建 `worldquant_alpha/wd_lib_wrapper.py`，用 `requests` + HTTP Basic Auth 直连 `https://api.worldquantbrain.com/`，自实现 `run_backtest`（POST `/simulations` → 轮询 `Location` 进度，按 `Retry-After` 等待，取 `alpha` 作为 `platform_id` 返回）、`get_alpha_details`（`GET /alphas/{id}`）、`get_alpha_check`（`GET /alphas/{id}/check`）、`self.session`（供 `update_alpha_properties` 用）。⚠️ 不要用 `wd_lib` 自带的 `run_backtest`——它内置"20 分钟超时 + 随机 10~60 分钟睡眠"逻辑，会卡死挖矿循环。
- **cwd 坑**：后台任务的 cwd 不一定是 `worldquant_alpha`。脚本顶部必须用 `os.path.dirname(os.path.abspath(__file__))` 把**脚本自身目录**加入 `sys.path[0]`、`load_dotenv` 也用同路径，绝不能依赖 `os.path.abspath(".")` 或 `cd`。
- **孤儿模拟 429（最阴的坑）**：`TaskStop` 杀掉本地 Python 进程时，**服务端已提交的回测仍在跑**，它们一直占用账户的"并发模拟数上限"（CONCURRENT_SIMULATION_LIMIT，通常很小如 2）。后果：新提交全部 `429 CONCURRENT_SIMULATION_LIMIT_EXCEEDED`，连第一条都失败（配额在 t=0 就被孤儿占满）。`/users/self/simulations`(404) 与 `GET /simulations`(405) 都查不了、也取消不了孤儿——它们只能**在服务端自己跑完才释放配额**。
- **429 应对模式（已验证有效）**：`run_backtest` 对 429 做**频繁短退避重试**（`wait = min(20 + attempt*8, 45)` 秒，最多 ~40 次 ≈ 20min），**绝不因限流丢弃候选**；加全局 `threading.Semaphore(2)` 限同时在飞提交；把每数据集并发降到 2（总 4 线程）。提交成功数会随孤儿释放而回升（已观测到从 0 → 2 条成功提交）。
- **"不停直到找到 2 个"必须靠重循环**：原 `main()` 只跑 Pass1+Pass2 一轮就退出。改成 `mine_dataset` **无限重循环**（每轮未集满 sleep 300s 再循环，最多 40 轮 ≈ 3.3h），并在 `mine_pass` 内**跳过已计入 `found` 的表达式**（去重，避免重循环重复占配额）。
- **结论**：挖矿卡住时先区分"全局拥堵（rank(close) 也卡）"还是"孤儿模拟占满配额（全 429）"——二者对策不同，前者只能等集群缓解，后者靠耐心 429 重试等孤儿释放。

### 🔢 并发上限实测（"探索最佳并发设置"任务）
- **服务端并发模拟上限 C = 5**（实测，非猜）。方法：停掉所有本地挖矿进程（让自身孤儿释放）→ 用挖掘脚本真实 `SETTINGS`（`language=FASTEXPR`，之前探针误用 `FAST` 导致 400，是坑）→ 阶梯式提交 12 条 `rank(close)`（间隔 0.3s）。结果：**前 5 条全部 201 接受，第 6 条起 `429 CONCURRENT_SIMULATION_LIMIT_EXCEEDED`**，首批连续接受数 = 5 → C=5。
- ⚠️ **429 报文不含数字**：`{"detail":"CONCURRENT_SIMULATION_LIMIT_EXCEEDED"}`，无法从报文读限额，只能靠"阶梯提交看首批接受数"实测。`/users/self` 也**不含**并发/模拟限额字段（已全量遍历 top-level + 嵌套键确认），勿再浪费时间查该接口。
- **最佳并发 = 5 在飞**（= min(本地线程, C)）。早期"4 线程"实测为**欠利用**（C=5 时 4 仅用满 80%）。
- **信号量必须包住整条回测**：原 `threading.Semaphore` 只在 `POST /simulations` 那一瞬间 `with` 生效，轮询等待期间信号量已释放 → 实际在飞数 = 工作线程数（4），而非 2 → 超额提交、疯狂 429。**修复**：把 `with self._sub_sem:` 提到 `run_backtest` 方法最外层，覆盖"提交+轮询"全程，使在飞数恒 = 信号量值。
- **最终配置**：`wd_lib_wrapper.py` 信号量 `2 → 5`（=C）；`mine_usa_ppa_multi.py` 每数据集线程 `2 → 3`（共 6，信号量 5 卡在飞、多 1 个缓冲线程随时补位）。验证：重启后成功提交从 0→1→2 随探针孤儿(5条 rank(close))释放而爬升，且无自身超额提交——证明在飞数被精确锁定在可用槽位数。
