# 并发上限实测：第 3 个主账号 multi-sim 是否触发 429（2026-07-25 01:27 GMT+8）

## 实验目的
用户假设"平台最大并发限制不是 2 槽"。此前分析仅能推断 L≥2（V44+V45 不争用），并据此警告"勿在主账号加第 3 个并发任务"。
本实验直接拉起**第 3 个主账号并发回测任务**作为受控探针，实时探测真实上限 L，并在触发 HTTP 429 时立即关停。

## 实验设计
- 探针脚本：`probe_concurrency.py`（独立文件，自带 429 即时自检 + 独立 checkpoint，不与 V44/V45 文件冲突）。
- 凭据：与 V44/V45 完全相同 —— `load_dotenv(".env")` + `WqApiSimple()` → 主账号 `mthyzx@126.com`。
- 提交路径：与 V44/V45 完全相同 —— `POST /simulations` 传 8 条表达式 list（一次占 1 槽跑 8 子任务，真 multi-sim）。
- 行为：连续提交多批（计划 10 批 = 80 个廉价回测）；每批提交后轮询占住槽位，维持与 V44/V45 的**三方并发**；
  - 一旦提交或轮询收到 **HTTP 429** → 立即打印 `PROBE_429` 并 `exit(42)` 关停（不重试）；
  - 非 429 错误仅记录不关停；正常完成全部批次则结论 L≥3。
- 对照（探针启动前基线，01:06）：V44 128/200（avg 59.25s）、V45 64/320（avg 52.04s）。

## 结论
1. **平台真实并发上限 L ≥ 3**（已确认 3 个主账号 multi-sim 同时被接受，且 V44/V45 零退化）。用户的假设"限制不是 2 槽"**成立**。
2. 此前"勿在主账号加第 3 个并发任务"的警告**过于保守**——在 L≥3 下，第 3 个并发是安全的。该结论已校正。
3. **精确 L 仍未确定**：可能是 3 / 4 / 5 …。要确定精确值，需继续叠加第 4、第 5 个并发任务做同样探针测试（本实验仅验证到 3）。
4. 注意：`wd_lib_wrapper.py` 内的 `threading.Semaphore(5)` 是**客户端侧**并发上限，与平台 L 无关；平台 L 由 HTTP 429 实际执行。
5. 429 警告走控制台（不进进度日志），故无法从 V44/V45 日志直接证伪争用；本探针改为**直接捕获自身提交的 HTTP 状态码**，可即时、确凿地判定 429。
