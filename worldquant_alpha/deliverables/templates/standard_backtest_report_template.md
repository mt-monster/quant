# 标准报告模板 · WQ PPA 因子挖掘监控 / 盘点 / 效率分析

> **用途**：本文件是后续所有"盯回测 / 看进度 / 盘点挖掘任务 / 评测可提交 alpha"类报告的**唯一标准依据**。
> 任何一次汇报都必须沿用本模板的四层逻辑框架与模块规范，不得自创结构、不得遗漏强制章节、不得编造数字。
> 配套生成器：`deliverables/tools/build_md_report.py`（单账号/主账号）、`build_global_overview.py`（多账号合并）。
> 关联框架：`~/.workbuddy/skills/wq-backtest-monitor/SKILL.md`。

---

## §0 模板使用说明（每次出报告前必读）

| 项 | 规范 |
|---|---|
| 适用范围 | 任何 WQ BRAIN PPA alpha 挖掘的监控 / 盘点 / 效率 / 提交核查汇报 |
| 逻辑骨架 | **背景概述 → 分析维度 → 核心发现 → 结论与建议**（四层递进，形成分析闭环） |
| 贯穿线 | ① 监控盲点扫描（D8）② 数据溯源校验（诚实性）③ 铁律（机器级进程枚举第一视角）—— 三者贯穿全篇 |
| 数字来源 | 全部来自 checkpoint / progress / CSV 文件**实算**；不得硬编码、不得凭印象 |
| 强制章节 | 提交核查（三级分类）、在飞任务 ETA——**每次不可省略** |
| 输出格式 | 优先 Markdown（`.md`），附 `present_files` 交付；HTML 备选 |
| 命名 | `deliverables/reports/<类型>_<YYYYMMDD_HHMM>.md`（类型：factor_mining_report / global_overview / backtest_monitor_report） |

**分析闭环示意**：
```
背景概述(为什么看、看什么、口径)
   │
   ▼
分析维度(D1–D7 体系化展开，D8 盲点贯穿)
   │
   ▼
核心发现(汇总表 + 分维发现 + 全局视图 + 逐项核查)
   │
   ▼
结论与建议(结论先行 → 问题 → 行动 → 风险)
   ▲                                          │
   └──────────── 数据溯源回写 / 盲点补充 ──────┘
```

# 第一部分 · 背景概述（Background & Scope）

> **目的**：让读者 30 秒内理解"这份报告为什么产生、看什么、边界在哪、数字怎么来的"。定调后续所有分析。

### 1.1 报告目的与触发场景
- **必填**：本次汇报的触发原因（用户请求 / 定时盘点 / 异常告警）。
- **必填**：一句话核心结论预告（结论先行的简版，详见 §3/§4）。
- **填写规范**：用 1–2 句说明"本快照要回答什么问题"。

### 1.2 监控范围与边界
- **必填**：纳入监控的账号与任务清单（主账号 / 独立账号 tri_track / tabbit / continuous_undug / green_guard / scan_rescue 等）。
- **必填**：是否多账号合并（决定用 build_md_report.py 还是 build_global_overview.py）。
- **填写规范**：逐账号标注"挖矿 / 检查器 / 调度器"性质，避免把检查器当挖矿量。

### 1.3 口径与定义（关键术语，每次统一复述）
| 术语 | 定义 | 易错点 |
|---|---|---|
| 研究回测总量 | 记失败回测的账号（主账号）的 `checkpoint.results` 条数 | 独立账号只记获 alpha_id 的成功提交，**不记失败**，故其真实回测 > 提交日志 |
| 平台 alpha 创建记录 | 各账号获 alpha_id 的提交日志合计 | 与研究回测**两口径不可相加** |
| PASS_CHEAP / CHECK_PENDING | 仅研究仿真 IS 廉价闸门通过 | **≠ 可提交** |
| found_alphas | 跨过生产相关性验证（有 prod_corr 字段）者 | 全局极少 |
| ACTIVE | 已真实提交至平台（status=ACTIVE） | 唯一确证"上线" |
| 候选池 | 有 IS 指标、待 OOS 验证者 | 提交路线 = 跑生产仿真 → /check → submittable → submit |

### 1.4 方法论铁律（发现入口）
> **第一视角必须是机器级全量 Python 进程枚举**：`Get-CimInstance Win32_Process -Filter "Name='python.exe'"`。
> **绝不**只用 `scan_v*` 过滤或靠 `*_progress_*.log` / v 系列日志发现任务（日志仅作 scan 脚本明细补充）。
> 理由：非标准命名的真实挖掘任务（如 `tabbit_option9.py`、`tri_track_undug.py`、`continuous_undug.py`）会被漏报。

# 第二部分 · 分析维度（Dimensions）— 体系化展开

> **目的**：把"盯回测"拆成 7 个互相关联、覆盖全面的维度，每个维度独立成章、逻辑递进。
> D1→D3 是"过程盘点"（在跑什么、跑多快），D4→D5 是"产能与质量"（出了什么、能不能交），D6 是"时间预期"，D7 是"失败归因"，D8 贯穿全程（防漏报）。

### D1 维度一 · 进程全景盘点（发现入口）
- **目的**：机器级确认"当前有哪些挖掘任务在飞、是什么、归谁"。
- **数据来源**：PowerShell `Get-CimInstance Win32_Process` 全量枚举 → 按命令行正则分类。
- **分类标准**：

  | 分类 | 正则 | 挖 alpha? |
  |---|---|---|
  | SCAN | `scan_v\d+` | ✅ 主账号 |
  | MINING | 非 scan_v 但真在挖 | ✅ 独立账号 |
  | MCP-SVC | `platform_functions\|mcp\|brain` | ⚠️ 服务端回测宿主（本机不跑计算、不写本地日志） |
  | WATCHDOG/TRACKER | `watchdog\|tracker` | ❌（但非 scan_v 命名的挖掘须人工改判） |
  | EDITOR | `jedi\|ms-python` | ❌ |

- **必填内容**：对每个真挖掘进程报 PID / 启动时间 / 线程数 / 内存 / 累计 CPU（CPU 极低=网络等待型，典型回测进程）。
- **常见陷阱**：① 只认 `scan_v*` 漏独立账号；② 把 `tri_track` 误判为 TRACKER；③ 把 MCP-SVC 当挖矿量。

### D2 维度二 · 逐任务并发模型与进度
- **目的**：每个在飞任务的"配置档 + 完成度 + 吞吐"。
- **数据来源**：读脚本确认 `BATCH_SIZE` / `CONCURRENCY` / `COOLDOWN` / 数据集 / 账号；读 checkpoint/CSV 确认 done / 候选 / 最佳 Sharpe。
- **必填内容**：
  - 并发配置表（任务 / 账号 / BATCH / CONCURRENCY / 数据集）
  - 进度表（任务 / done / total / 候选数 / 最佳S / 吞吐=done÷已运行分钟）
- **填写规范**：吞吐单位用 `α/hr`；标注是否跑在该账号/配置的最大并发档。

### D3 维度三 · 回测效率分析
- **目的**：算清"跑得快不快、槽位浪费没、还能怎么提"。
- **数据来源**：D2 的吞吐 + 基准（`bench_v34_sim_speed`：multi(8)=86.1 α/hr vs single=54.3 α/hr，speedup 1.59×）+ 并发令牌桶模型（C≈7）。
- **必填内容**：
  - 实测吞吐 vs 基准对比
  - 平台并发利用率（同时跑几个作业、槽位是否闲置）
  - 提吞吐杠杆排序（关闲 MCP 宿主释放主账号槽位 / 复制独立账号模式 / multi-sim 批量）
- **结论锚点**：当前真正瓶颈 = **信号发现不是吞吐**（并发批次首步 Sharpe 远低于闸门）。

### D4 维度四 · 候选产能与质量漏斗
- **目的**：把"回测量"转化为"可交付产能"，量化每一层的损耗。
- **数据来源**：各 checkpoint `results[].status` + `found_alphas[]`。
- **必填漏斗表**（层级递进）：

  ```
  研究回测总量
    → 过 IS 廉价闸门 (PASS_CHEAP + CHECK_PENDING)
      → 跨生产相关性 (found_alphas, prod_corr)
        → 跑过 OOS 生产仿真
          → 平台 submittable
            → 真实提交 ACTIVE
  ```

- **填写规范**：每层标注数字 + 转化率 + 当前卡在哪层（全局通常卡在"OOS 生产仿真"或"生产相关性"）。

### D5 维度五 · 提交就绪四关审计（核心质量门）
- **目的**：逐候选判定"离真正提交还差几关"，**绝不称 PASS_CHEAP 为可提交**。
- **四关层级**：

  | 关 | 内容 | 取证方式 |
  |---|---|---|
  | ① 研究仿真 IS | S>1.58/F>1.0/TVR∈[0.05,0.30]/M>10bp/Ret>0.05 | checkpoint `results[].status` |
  | ② 生产仿真 OOS | 样本外稳健 | 是否跑过 OOS（通常 0） |
  | ③ 生产相关性 | PROD_CORRELATION+SELF_CORRELATION<0.7 | checkpoint `found_alphas[]`（含 prod_corr） |
  | ④ submittable+submit | 平台判定 + 真实落平台 | 脚本 `no_submit`? / 是否显式 submit |

- **必填**：三级分类表（✅ 已正式提交 / ✅ 回测完成待提交 / 🔶 仍需验证）+ 逐候选明细（pid/任务/S/已完成验证项/缺步骤/建议）。
- **结论模板**："`N` 个候选，`M` 已提交，`K` 回测完成待提交，`N-M-K` 仍需验证"。

### D6 维度六 · 在飞任务 ETA（强制章节）
- **目的**：每个在飞任务给墙钟预期完成时间。
- **数据来源与算法**：
  - ds 舰队：`*_progress_*.log` 取 done/total/elapsed → remaining÷(done÷elapsed) + now
  - tri_track：分片完成数÷总分数 × 每分片~300s ÷ CONCURRENCY
  - 无进度日志者（如 v52b）：标 **未知** + 原因（仅写 checkpoint）+ 建议补 progress 日志
  - 开放型（如字段遍历无固定总数）：ETA 开放，报实时吞吐 + "至耗尽或手动停止"
- **必填**：ETA 汇总表（任务 / 当前进度 / 预期完成 / 置信度）。
- **置信度标注**：运行 <30min=低 / 30–60min=中 / >60min=较高。

### D7 维度七 · 失败闸门与风险归因
- **目的**：解释"为什么产能低 / 卡在哪"，定位信号方向问题 vs 工程问题。
- **数据来源**：checkpoint 中 FAIL/PENDING 记录的 `failed_gates` 字段、各 `status` 分布。
- **必填**：失败闸门分布表 + 主要归因（如 PROD_CORRELATION 过高=信号方向被占用；LOW_SUB_UNIVERSE_SHARPE=子宇宙不达标；universe 非法档位=400 拒）。
- **填写规范**：区分"结构性无解（需换信号方向）"与"工程可调（换档位/调参）"。

### D8 [贯穿] 监控盲点扫描（防漏报，每次必做）
- **目的**：主动排查"报告还可能漏了什么"，弥补 D1 的盲区。
- **盲点分类（逐类排查，缺一不可）**：

  1. **硬编码任务列表**：只列固定 V 号会漏新批次 → 用进度日志 + checkpoint 自动发现。
  2. **服务端 / WQ-BRAIN 任务无本地日志**：仅经 WQ 控制台 / MCP 对话可见。
  3. **账号维度盲区**：不同账号任务互不可见 → 多账号用 global_overview 合并。
  4. **只写 checkpoint、不写进度日志的 scan**：扫 `results/*checkpoint*.json` 未登记者，近期更新且命中在飞线索则标"在飞扫描"。
  5. **非 scan_v 命名的真实挖掘任务**：必须人工改判单列（见 D1 陷阱）。

# 第三部分 · 核心发现（Core Findings）

> **目的**：把 D1–D8 的散点分析收敛成"一眼看懂"的汇总 + 分维度结论 + （多账号时）全局视图 + 逐项核查。

### 3.1 核心指标汇总表（结论先行的数据版）
- **必填字段**：累计研究回测 / 候选数(PASS_CHEAP+CHECK_PENDING) / found_alphas / ACTIVE 提交数 / 全链路最佳 Sharpe / 在飞任务数。
- **填写规范**：单行总览 + 与上次快照的环比（+N）。

### 3.2 逐维度发现摘要
- 对应 D1–D7 各给出 1–3 句"本维度关键发现"（不是复述数据，是**结论**）。
- 示例：D3"吞吐达标但信号发现是瓶颈"；D5"全局仅 1 个跨过生产相关性"。

### 3.3 全局合并视图（仅多账号报告）
- **必填**：各账号分列明细表（账号 / 性质 / 回测或提交数 / 候选 / ACTIVE）+ 合并指标（诚实标注两口径不可相加）。
- **填写规范**：参见 global_overview 报告第二章；scan_rescue 等主账号子任务**不得重复计入**合并总量。

### 3.4 逐项候选核查表（三级分类，强制）
- **必填**：✅ 已正式提交 / ✅ 回测完成待提交 / 🔶 仍需验证 三张表。
- **逐候选明细**：pid / 任务 / Sharpe / 已完成验证项 / 缺少步骤 / 操作建议。
- **红线**：绝不称 PASS_CHEAP 为"可提交"。

# 第四部分 · 结论与建议（Conclusions & Recommendations）

> **目的**：给决策者"该做什么"，形成分析闭环（发现→行动）。

### 4.1 结论先行（Executive Summary）
- **必填**：3–5 条硬结论（数字 + 判断），例如"全局仍仅 1 个 alpha 确证上线；44 候选卡 OOS 硬闸门"。
- **填写规范**：先结论后论据；与 §1.1 预告呼应。

### 4.2 问题说明
- 列出当前阻碍（信号方向 / 工程 / 额度 429 / 盲点未消除等），按影响排序。

### 4.3 行动建议（优先级排序）
- **必填**：带序号的下一步清单，每条含"动作 + 负责对象(账号/脚本) + 预期效果"。
- 示例：① 对主账号候选跑生产仿真→/check→submit（复制 YPgAa3WR 全流程）；② 回溯独立账号提交做 /check 核实；③ 统一 checkpoint 目录消除 total_N 低估。

### 4.4 风险与未决项
- 标注不确定性（ETA 未知项、盲点未闭合项、额度限制）与应对。

# 附录 · 方法论标准（Methodology，生成器与人工共用）

## A. 机器级进程枚举标准
```powershell
Get-CimInstance Win32_Process -Filter "Name='python.exe'" |
  Select-Object ProcessId, CommandLine, ThreadCount, WorkingSetSize, UserModeTime, CreationDate
```
- 第一视角；分类见 D1；独立账号任务人工改判单列。

## B. 四关提交审计标准
- 见 D5；取证函数：`collect_submittable()`（status∈{PASS,PASS_CHEAP}）取候选；`collect_verified_pids()`（found_alphas 的 pid）取真正过生产相关性者。两者差集 = "廉价 IS 闸通过但未验生产关"。

## C. ETA 计算标准
- 见 D6；公式统一为 `remaining_work ÷ throughput + now`；无日志者标"未知"。

## D. 监控盲点分类标准
- 见 D8 五类；每次报告 §3 / 第十二章（主账号报告）或独立盲点段必须逐类排查。

## E. 数据溯源与诚实性规范
1. 所有数字来自文件实算，不硬编码、不凭印象。
2. 两口径（研究回测 vs 提交记录）不可相加，合并时显式标注。
3. 子任务（如 scan_rescue）已计入父账号者，合并时不重复加。
4. 生成器修正后必须复跑校验：grep 残留字面量（如 `{var}` 未替换）、矛盾数字（总数≠分项之和）。
5. 报告末尾标注：生成器名 + 快照时间 + "数字均来自文件实测，未编造"。
